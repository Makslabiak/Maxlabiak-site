# Экспресс-аудит сайта — документация

Инструмент, который открывается по кнопке «Проверить свой сайт» на первом экране.
Посетитель вводит адрес своего сайта, получает отчёт с баллом, разбором по пяти
направлениям и списком проблем, а затем может оставить заявку на ручной разбор.

---

## 1. Что реализовано

**Интерфейс** — модальное окно на чистом JS, без фреймворков и внешних библиотек:

- ввод адреса с валидацией на клиенте и на сервере;
- экран анализа: пять этапов со статусами и прогресс-бар, который плавно
  подползает к 90% и доходит до 100% только по ответу сервера;
- отчёт: общий балл круговым индикатором на SVG, пять карточек категорий,
  список проблем, блок «что сделано хорошо», сворачиваемые технические метрики
  с пояснениями простым языком;
- продающий блок и форма заявки;
- экраны ошибки, частичного результата и успешной отправки.

**Сервер** — Node.js + Express:

- Google PageSpeed Insights (мобильная стратегия), сжатие отчёта Lighthouse
  в компактную структуру;
- разбор HTML страницы через cheerio — около 35 проверок;
- скриншот первого экрана на телефоне через Playwright, плюс чтение реальных
  позиций элементов (виден ли заголовок и кнопка без прокрутки);
- система оценки с настраиваемыми весами;
- отправка заявки в Telegram;
- защита от SSRF, ограничение частоты запросов, кэш, mock-режим.

## 3. Изменённые файлы

`index.html` — три точечные правки, вёрстка не тронута:

1. `<link rel="stylesheet" href="assets/css/site-audit.css">` в `<head>`;
2. атрибут `data-audit-open` на кнопке «Проверить свой сайт» в hero
   и на кнопке «Узнать» в CTA-полосе. `href="#brief"` **оставлен намеренно**:
   если JS не загрузился, кнопки продолжают вести на бриф;
3. `<script src="assets/js/site-audit.js" defer></script>` перед `</body>`.

## 4. Установка и запуск

```bash
cd "site dars"
npm install
npx playwright install chromium
cp .env.example .env
npm run dev
```

Открыть http://localhost:3000 — Express отдаёт и сайт, и API с одного порта,
поэтому CORS не нужен.

Команды:

| Команда | Что делает |
|---|---|
| `npm run dev` | запуск с автоперезагрузкой при правке файлов сервера |
| `npm start` | обычный запуск |
| `npm test` | 57 тестов критичных частей |
| `npm run playwright:install` | доустановка браузера |

### Если правишь только вёрстку

Можно открыть `index.html` любым статическим сервером (Live Server, `python3 -m
http.server 8080`). Фронтенд сам определит, что API живёт на `localhost:3000`, и
будет обращаться туда. Сервер при этом всё равно должен быть запущен.

### Playwright на старых macOS

На macOS 12 и ниже свежие версии Playwright не устанавливают свой Chromium
(«does not support chromium on mac12»). Код это учитывает: если своего браузера
нет, запускается установленный в системе Google Chrome. Отдельных действий не
требуется, в логе будет запись `bundled_chromium_unavailable`. На боевом
Linux-сервере отработает штатная ветка.

## 5. Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PORT` | нет | порт сервера, по умолчанию 3000 |
| `PAGESPEED_API_KEY` | нет | ключ Google PageSpeed. Без него блок скорости недоступен, остальной аудит работает |
| `TELEGRAM_BOT_TOKEN` | для заявок | токен бота от @BotFather |
| `TELEGRAM_CHAT_ID` | для заявок | куда слать заявки |
| `AUDIT_SCREENSHOT_TTL_HOURS` | нет | через сколько часов удалять скриншоты, по умолчанию 24 |
| `AUDIT_MOCK_MODE` | нет | `true` — отдавать тестовый отчёт |
| `AUDIT_MOCK_SCENARIO` | нет | `good` / `average` / `bad` / `random` |
| `AUDIT_RATE_LIMIT_WINDOW_MIN` | нет | окно ограничения, по умолчанию 15 минут |
| `AUDIT_RATE_LIMIT_MAX` | нет | сколько аудитов с одного IP за окно, по умолчанию 5 |
| `AUDIT_CACHE_TTL_MIN` | нет | сколько минут переиспользовать результат, по умолчанию 45 |

Ключи читаются только на сервере и во фронтенд не попадают.

## 6. Mock-режим

Нужен, чтобы править интерфейс, не тратя квоту API и не ожидая по минуте
каждый прогон. Обращений к PageSpeed и Playwright не происходит, реальный
домен не требуется — можно вводить любой выдуманный адрес.

```bash
AUDIT_MOCK_MODE=true AUDIT_MOCK_SCENARIO=bad npm run dev
```

Сценарии дают предсказуемый разброс: `good` ≈ 94 балла и три мелких замечания,
`average` ≈ 65 и полтора десятка проблем, `bad` ≈ 24 и три десятка. Mock-данные
прогоняются через тот же конвейер правил, что и настоящие, — поэтому тестовый
отчёт не расходится с реальным при изменении правил.

**В production `AUDIT_MOCK_MODE` должен быть `false`.**

## 7. Проверка PageSpeed

Ключ бесплатный: Google Cloud Console → включить *PageSpeed Insights API* →
Credentials → API key. Положить в `.env` как `PAGESPEED_API_KEY`.

Проверить, что сервер его видит:

```bash
curl -s localhost:3000/api/health
# {"ok":true,"mock":false,"pagespeed":true,"telegram":true}
```

Реальный аудит из терминала:

```bash
curl -s -X POST localhost:3000/api/audit \
  -H "Content-Type: application/json" \
  -d '{"url":"example.com"}'
```

Без ключа запросы всё равно уходят, если выставить `PAGESPEED_ALLOW_NO_KEY=true`,
но Google быстро начнёт отвечать 429. Штатное поведение без ключа: категория
«Скорость» помечается как недоступная, её вес исключается из общего балла,
посетитель видит сообщение о частичном результате.

## 8. Настройка Telegram

1. Написать @BotFather, создать бота, забрать токен.
2. Узнать свой chat id у @userinfobot (или id канала, если заявки идут туда).
3. Написать боту любое сообщение — иначе он не сможет ответить первым.
4. Заполнить `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env`, перезапустить.

Пока Telegram не настроен, заявки пишутся в `server/temp/leads.json`.
**Это только для разработки.** JSON-файл не годится для боевой работы: нет
резервных копий, при одновременной записи возможны потери, нет поиска.
Для production сюда подключается CRM или база — точка расширения одна,
функция `sendLead` в `server/services/lead.service.js`.

Данные заявки сервер берёт **не из тела запроса**, а из своего хранилища по
`auditId` — иначе присланный фронтендом балл можно было бы подделать.

## 9. Production

Минимальный вариант:

```bash
npm ci --omit=dev
npx playwright install --with-deps chromium
AUDIT_MOCK_MODE=false pm2 start server/server.js --name dars-audit
```

Перед выкладкой проверить:

- [ ] `AUDIT_MOCK_MODE=false`;
- [ ] `.env` не в репозитории (уже в `.gitignore`);
- [ ] за nginx включён `trust proxy` — он уже стоит в `server.js`, иначе
      ограничение частоты увидит один IP на всех;
- [ ] Playwright установлен вместе с системными библиотеками (`--with-deps`);
- [ ] настроен Telegram, иначе заявки уйдут в файл.

## 10. Безопасность

Главный риск такого инструмента — SSRF: посетитель вводит адрес, а сервер
послушно идёт по нему. Если не проверять, через поле можно достучаться до
внутренней сети или до metadata-сервиса облака, откуда утекают ключи доступа.

Что сделано:

- разрешены только `http` и `https`, только порты 80 и 443;
- домен резолвится, и проверяются **все** полученные IP, а не первый;
- заблокированы loopback, приватные диапазоны IPv4 и IPv6, link-local,
  multicast, служебные сети, CGNAT, `169.254.169.254` и внутренние имена
  (`*.local`, `*.internal`, `metadata.google.internal` и подобные);
- `::ffff:127.0.0.1` разбирается как IPv4 — иначе через mapped-адрес можно
  было бы обойти проверку;
- редиректы обрабатываются вручную, каждый следующий адрес проверяется заново
  (публичный домен вполне может редиректить на `192.168.1.1`);
- не больше трёх редиректов, лимит HTML 2 МБ, таймауты на всё;
- логин и пароль в адресе не принимаются, cookies не передаются;
- Playwright ничего не нажимает, не отправляет формы и не проходит CAPTCHA;
- наружу не отдаются stack trace.

Проверить работоспособность защиты можно на домене `localtest.me` — он публичный,
но резолвится в `127.0.0.1`:

```bash
curl -s -X POST localhost:3000/api/audit \
  -H "Content-Type: application/json" -d '{"url":"localtest.me"}'
# {"success":false,"code":"blocked_target", ...}
```

## 11. Ограничения текущей версии

1. **TOCTOU в защите от SSRF.** Между проверкой DNS и самим запросом адрес
   теоретически может смениться (DNS rebinding). Полное закрытие требует
   привязки соединения к уже проверенному IP через собственный
   `undici.Agent` — отложено, чтобы не тащить зависимость в MVP.
2. **Кэш и хранилище отчётов в памяти.** При перезапуске теряются, между
   несколькими экземплярами сервера не разделяются. Интерфейс
   `cache.service.js` намеренно повторяет Redis — замена локальная.
3. **Скриншот в JPEG, а не WebP.** Playwright умеет только png и jpeg,
   для WebP понадобился бы `sharp` (около 30 МБ зависимостей).
4. **Прогресс-бар не привязан к реальным этапам сервера** — API отдаёт
   результат одним ответом, промежуточных событий нет. Шкала движется
   правдоподобно и не доходит до 100% раньше ответа, но это оценка.
   Точная привязка потребует SSE или опроса статуса.
5. **Desktop-стратегия PageSpeed не запускается** — код параметризован,
   но лишний запрос удваивает время и расход квоты.
6. **Анализ первого экрана — эвристика.** Где данные ненадёжны, отчёт
   говорит «не удалось обнаружить», а не «нет».
7. **Заявки без Telegram уходят в файл** — см. раздел 8.
8. **CSP в helmet отключён**: `index.html` держит весь CSS и JS инлайном.
   Включать имеет смысл вместе с выносом инлайнового кода.

## 12. Как подключить AI vision-анализ первого экрана

Архитектура к этому готова: у правил в `report.service.js` три независимых
источника — `data.html`, `data.ps` и `data.viewport`. Vision становится
четвёртым.

1. Создать `server/services/vision.service.js` с функцией, принимающей путь
   к скриншоту и возвращающей структуру вида
   `{ clarity: 0..1, hasOffer: bool, notes: [] }`.
2. Вызвать её в `audit.controller.js` рядом с PageSpeed — в том же
   `Promise.all`, тем же необязательным источником: упала — отчёт всё равно
   собирается.
3. Положить результат в `data.vision` и добавить правила в `ISSUE_RULES`
   с `source: 'vision'`.
4. Ключ модели — только в `.env`, вызов только с сервера.

Обязательным для запуска делать не нужно: без ключа `data.vision` остаётся
`null`, и правила просто не срабатывают.
